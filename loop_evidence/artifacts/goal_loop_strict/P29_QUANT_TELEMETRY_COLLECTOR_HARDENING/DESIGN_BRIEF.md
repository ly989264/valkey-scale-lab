# DESIGN_BRIEF - P29_QUANT_TELEMETRY_COLLECTOR_HARDENING

## Stage Objective

Harden the quantitative telemetry foundation before strict real 50/100/200 stages run. P29 must produce a bounded small real Valkey collector proof with schema-validated `events.jsonl`, `metrics_timeseries.jsonl`, `workload_windows.json`, `quant_summary.json`, `coverage_ledger.json`, and `telemetry_completeness_report.json`, while making missing data explicit and never claiming large-scale management/fault/lifecycle matrix coverage.

## Current Repo Facts

- `docs/codex/goal-loop-strict/stages/P29_QUANT_TELEMETRY_COLLECTOR_HARDENING.md` requires event/metric JSONL writers, workload aggregation, topology snapshots, Valkey INFO / CLUSTER INFO / CLUSTER NODES samplers, Docker/process stats where available, missing-data encoding, provenance writing, schema validation, and a small real Valkey collector proof with at least 6 nodes.
- `codex/phase_manifest.json` already declares P29 as `real_valkey_required=true`, `max_nodes=6`, with `real_valkey_e2e`, `quant_completeness`, `assert_exact_scale_real_evidence --min-nodes 6`, and cleanup gates.
- `src/valkey_scale_lab/metrics/__init__.py` already has `TelemetryRun`, `write_jsonl`, `workload_metrics`, missing constants, and error classification, but emitted rows use `phase_id` and do not currently include strict `stage_id`, `coverage_id`, `scale`, or `node_count` fields required by `docs/codex/goal-loop-strict/07_QUANTIFICATION_DATA_CONTRACT.md`.
- `src/valkey_scale_lab/runtime/docker_runtime.py` has P16 telemetry artifact generation and helpers for Valkey INFO, CLUSTER INFO, CLUSTER NODES, Docker stats, and workload windows. P29 scenario `strict_telemetry_small_real` is not yet in `create_scenario` allow-list; this is a likely implementation blocker.
- `src/valkey_scale_lab/workload/__init__.py` creates the six canonical windows and workload metric rows, but window metrics currently use `start_event_id` / `end_event_id`; strict contract names `window_start_event_id` / `window_end_event_id` inside each window metric set as well.
- `scripts/assert_quant_completeness.py` is currently too shallow for P29: it checks artifact presence and a few runtime claim flags, but not line-by-line schemas, forbidden `null`/`NaN`/`undefined`, required strict fields, missing reasons, workload window field completeness, event-id linkage, provenance, or telemetry source coverage.
- `schemas/artifact/goal_loop_event.schema.json` and `schemas/artifact/goal_loop_metric_sample.schema.json` validate current goal-loop rows but do not require strict fields from the P29 contract. They also allow string timestamps and `additionalProperties`.
- `schemas/artifact/workload_windows.schema.json` only requires `window_name`, `start_event_id`, `end_event_id`, and `metrics`; it does not enumerate required workload metrics or reject forbidden missing representations.
- `artifacts/coverage/strict_coverage_registry.json` and `artifacts/coverage/strict_scenario_plan.json` were generated by P28. All real 50/100/200 coverage rows remain `PENDING`; P29 must not change them to `PASS`.

## Exact Implementation Plan

1. Add a strict telemetry model layer while preserving backward-compatible fields:
   - Extend `TelemetryRun` or add a P29-specific strict telemetry context with `stage_id`, `coverage_id`, `scale`, `node_count`, `clock_source`, and wall/monotonic timing.
   - Keep `phase_id` for existing schemas and consumers, but emit `stage_id` as an alias for strict artifacts.
   - Make JSON serialization reject `None`, `NaN`, `Infinity`, empty missing reasons, and empty JSONL rows before writing.

2. Implement P29 collector artifact generation:
   - Add P29 scenario support for `P29_QUANT_TELEMETRY_COLLECTOR_HARDENING/strict_telemetry_small_real` in `src/valkey_scale_lab/runtime/docker_runtime.py`, capped to exactly the 6-node config.
   - Reuse existing real 6-node Docker scenario setup; no large-scale or >200 runtime paths.
   - Sample each node for Valkey INFO, CLUSTER INFO, CLUSTER NODES, and topology snapshot rows.
   - Collect Docker stats where container runtime is available; encode unavailable Docker/process stats as `MISSING` or `SKIPPED_WITH_REASON` with a reason.
   - Run the canonical six workload windows with observed latencies and error counts; compute percentiles from real samples only.
   - Write a `telemetry_completeness_report.json` summarizing source coverage, schema validation status, missing-data counts, provenance refs, and fail/pass decision.
   - Write `coverage_ledger.json` as a copy/projection of the P28 registry with rows still `PENDING` and `stage_id=P29...`; include P29 validation artifact refs only in report/provenance, not as `PASS` matrix coverage. 待验证: whether existing postcheck expects `coverage_ledger.json` to contain all rows or only P29-relevant rows; schema currently requires strict registry shape and IDs only for matrix rows.

3. Add provenance:
   - `quant_summary.json.artifact_refs` must include all P29 required artifacts.
   - Add `source_artifacts` and hashes in `telemetry_completeness_report.json` for `events.jsonl`, `metrics_timeseries.jsonl`, `workload_windows.json`, `valkey_e2e_evidence.json`, `cleanup_report.json`, and `coverage_ledger.json`.
   - Include producer, commit SHA if available, schema paths, and validation command outputs or result summaries. 待验证: exact commit SHA source during gate execution should be `git rev-parse HEAD`, falling back to `MISSING` only with reason.

4. Harden validation:
   - Strengthen `scripts/assert_quant_completeness.py` for P29 without weakening existing P16-P26 behavior.
   - Validate JSONL line-by-line using `scripts/schema_validator.py` plus P29-specific field checks.
   - Reject `null`, `NaN`, `Infinity`, `undefined`, empty string placeholders, field omission, and `0` used with an explicit placeholder flag/reason pattern.
   - Require metric rows for `valkey_info`, `cluster_info`, `cluster_nodes`, `docker_stats` or a reasoned missing row, and `workload`.
   - Require all canonical workload windows, each required metric, event-id links into `events.jsonl`, and missing reasons for each `MISSING` value.
   - Require `quant_summary.counts` to match artifact line/window counts and `runtime_claims.real_valkey_claimed=true`, `management_runtime_claimed=false`, `fault_runtime_claimed=false`.

5. Strengthen schemas carefully:
   - Prefer adding P29-specific schemas such as `schemas/artifact/strict_telemetry_completeness_report.schema.json`, and optionally `strict_goal_loop_event.schema.json` / `strict_goal_loop_metric_sample.schema.json` if changing global schemas would break historical artifacts.
   - If updating existing `goal_loop_event` and `goal_loop_metric_sample`, keep compatibility for historical `phase_id` rows or adjust tests/artifacts intentionally. Do not silently relax fields.
   - Add schema/tests for `telemetry_completeness_report.json` instead of relying on generic `strict_generic_report.schema.json` if feasible.

6. Update gates and tests:
   - Keep required P29 stage gates from the stage doc.
   - Add unit tests for missing-data encoder, strict JSONL rejection cases, workload window completeness, and P29 quant completeness failures.
   - Add integration/runtime tests that P29 scenario is six-node only and does not admit 50/100/200 or >200 execution.
   - Add assertion tests proving invalid JSONL, missing reasons, missing workload fields, fake real evidence, and absent provenance fail closed.

## Safety Constraints

- Do not default to 1000 nodes.
- Do not run 50/100/200 real matrix scenarios in P29.
- Do not start any real runtime above 200 nodes.
- P29 real proof is capped at the existing 6-node small config.
- Do not mutate host network, firewall, routes, PF, nftables, iptables, host interfaces, or OS network services.
- Fault injection is out of scope for P29 except passive telemetry readiness; do not introduce host-level fault paths.
- All Docker/process resources must remain owned, labeled, deterministic, collision-checked, and cleaned up through existing cleanup paths.

## Blocking Conditions

- Docker or Valkey runtime unavailable for the 6-node real proof.
- `strict_telemetry_small_real` cannot be implemented without weakening runtime safety caps.
- JSONL writer accepts invalid rows, `null`, `NaN`, `Infinity`, `undefined`, omitted required fields, or `MISSING` without a reason.
- Workload windows contain fabricated percentiles or omit required metrics.
- Docker/process stats unavailable without reasoned `MISSING` / `SKIPPED_WITH_REASON` encoding.
- `telemetry_completeness_report.json` lacks provenance from raw artifacts to summaries.
- Cleanup fails or leaves owned resources.
- Any P29 artifact or review claims large-scale 50/100/200 matrix coverage.

## Review Focus Points

- Verify P29 only implements telemetry hardening and 6-node collector proof.
- Verify every metric/event line is parseable, schema checked, and has strict fields.
- Verify missing data is explicit and no placeholders are used.
- Verify workload percentiles come from observed latency samples.
- Verify topology/Valkey/Docker/process samplers record either measured values or reasoned missing states.
- Verify `quant_summary`, `telemetry_completeness_report`, and `coverage_ledger` agree on counts and claims.
- Verify `coverage_ledger.json` does not mark strict matrix rows as `PASS`.
- Verify cleanup evidence is real and passing.
